# ADR-028 — Portal Trabalhador Duas Portas (Produção + Pessoal)

**Código:** CSN-L2-SUP-ADR-028-2026  
**Data:** 31/03/2026  
**Estado:** ✅ Aceite  
**Sessão:** 33–34  
**Nível ISA-95:** L2-SUP (Supervisão / Interface Operacional)

---

## Contexto

O acesso dos trabalhadores no portal tinha uma navegação única para contextos com naturezas diferentes:

- **Produção** (obras, fases, timer, execução diária)
- **Pessoal/RH** (recibos, CITs, dados pessoais, conta corrente)

Na prática de fábrica, os operadores precisam de entrada rápida para execução (L2/L3-PRD), enquanto dados pessoais exigem maior controlo de privacidade e validação adicional (L3-RH). A ausência desta separação aumentava fricção operacional e risco de exposição indevida de dados RH no contexto produtivo.

---

## Decisão

Adotar o padrão **Portal Trabalhador Duas Portas**:

1. **Modo Produção**  
   Entrada direta (botão principal) para fluxo operacional.

2. **Modo Pessoal**  
   Entrada separada com **re-autenticação por PIN** para proteção de dados RH.

3. **Navegação por modo**  
   O menu (mobile/desktop) adapta-se ao modo selecionado, reduzindo ruído e limitando superfícies de erro.

4. **Persistência de sessão + comutação explícita**  
   O trabalhador pode regressar ao seletor de modo sem terminar sessão.

---

## Declaração Camada 2 vs Camada 3

| Componente | Camada | Papel |
|-----------|--------|-------|
| UI `ModeSelector`, `BottomNav`, vistas `Modo Produção`/`Modo Pessoal` | **Camada 2** | Interlocução e experiência de uso; não produz registos finais |
| Agentes e endpoints de domínio (`/api/timer`, `/api/kpis/worker`, `/api/rh/*`) | **Camada 3** | Execução de regras de negócio e produção de dados/documentos |

**Regra:** o Portal Duas Portas é mecanismo de interface (Camada 2). A lógica de produção/RH permanece no núcleo (Camada 3).

---

## Consequências

**Positivas**

- Reduz contexto misto entre execução produtiva e dados pessoais.
- Melhora usabilidade no chão de fábrica (acesso rápido ao modo de trabalho).
- Reforça privacidade no modo pessoal com re-auth por PIN.
- Facilita evolução independente dos dois percursos (PRD vs RH).

**Trade-offs**

- Mais estado de UI (modo ativo + navegação condicionada).
- Necessidade de manter consistência de permissões entre frontend e endpoints.

---

## Notas de Implementação

- `ModeSelector` e `workerMode` no `page.tsx`.
- `BottomNav` e sidebar condicionados por modo.
- Integração progressiva de funcionalidades por modo:
  - Produção: chat, obras, dashboard worker, documentos operacionais.
  - Pessoal: recibos, CITs, conta corrente, dados pessoais.
